Tokenomics

LOXLEY Tokenomics

⚠️

LOXLEY is not deployed. No token exists at any address on any chain. The parameters below describe what LoxleyBondToken does when it is deployed, taken from the contract source, not from a launch that has happened.

What the token is for

LOXLEY is collateral. Ciphernode operators bond it to join the pool that sortition draws committees from, and it is what gets slashed when an operator fails a duty. That is its function in the protocol — everything else the token does is a consequence of being ordinary enough to trade.

It is deliberately not the token that pays for computation. Requesters pay fees in a separate token with a different width; see Two tokens, two widths.

Powers the contract does not have

The interesting part of this token is what is missing from it. Every power a token contract holds is a promise somebody has to trust, and collateral is the worst place to ask for that trust: a token that can freeze a balance can freeze a bond.

So LoxleyBondToken has:

  • No mint. Supply is minted once, inside the constructor. There is no function that can increase it afterwards, so no amount of key compromise can dilute a holder.
  • No owner. No Ownable, no admin role, no upgrade path. There is nothing to renounce, because there was never anything to hold.
  • No pause, no blocklist, no transfer hook, no fee. Transfers cannot be stopped, taxed, or singled out.
  • No lock, no cliff, no vesting. lockedBalanceOf and lockedBalanceAt return zero, and they return it because it is true, not as a stub. Every balance is fully transferable from the moment it exists.

These are not claims about intent. They are claims about the bytecode, and they are checkable: read the source at packages/loxley-contracts/contracts/token/LoxleyBondToken.sol, then verify the deployed contract matches once it exists.

Distribution

The entire supply is minted to a single recipient at deployment. Where it goes after that — the Pons pool, an operator incentive reserve, anything else — is not enforced by the contract and is not claimed here.

This page does not publish an allocation chart. A pie with percentages implies commitments that are encoded somewhere and can be checked; nothing in this contract encodes them. When allocations are decided and locked in a contract that can be read, they get documented here, and not before.

Two tokens, two widths

Loxley uses two different tokens, and the registry checks both:

TokenDecimalsUsed for
BondLOXLEY18operator collateral, slashing
Fee / ticketUSDG6paying for computation, ticket collateral

The width difference is not cosmetic. BondingRegistry stores expectedCiphernodeBondDecimals: 18 and expectedTicketDecimals: 6, and rejects a token whose decimals() disagrees. Configuring an 18-decimal token as the fee token fails with a custom error carrying only (address, 6, 18) — which tells you nothing at all unless you already knew to look here.

Votes and the clock

The token extends ERC20Votes, which gives it checkpointed balance history. It is wired to timestamps, not block numbers:

function clock() public view override returns (uint48) {
  return uint48(block.timestamp);
}
 
function CLOCK_MODE() public pure override returns (string memory) {
  return 'mode=timestamp';
}

OpenZeppelin's default is block numbers, and the default is wrong here. BondedCheckpoints keeps its own history keyed by block.timestamp, and BondedVotes refuses to bind two histories whose clocks disagree — summing a timestamp-keyed history with a block-numbered one produces a number for two unrelated points in time, and nothing downstream could detect it. A plain ERC20Votes token reverts with ClockMismatch at deployment. That revert is the design working.
